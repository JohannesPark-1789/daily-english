# 세션 기록 (KST)

> 대화에는 날짜가 없어 시간 경과를 알 수 없다. 세션마다 여기에 KST 날짜로 남긴다.

## 2026-10-27 (화) — 예약은 멀쩡하다. 문제는 **지연**이었다

어제 "예약이 안 떴다"고 적은 것은 틀렸다. **늦게 떴을 뿐이다.**

- 10-26 예약 실행(40246287195)은 **08:46 KST** 에 떴고, 성공했다. 다만 내가 07:09 에 수동
  발송한 뒤라 올바르게 건너뛰었다:

  ```
  [WARN] 오늘(2026-10-26) 이미 50번을 보냈습니다 — 건너뜀
  ```

  → `lastSentDate` 중복 방지가 실제로 동작하는 것까지 확인된 셈이다.
- 오늘(10-27)도 07:05 까지 안 떠서 수동 발송했다 — **051 SO MUCH FOR THAT** (07:06:39).

### 지연 기록 — 전부 `분 = 0` 슬롯

| 날짜 | cron | 예정(KST) | 실제(KST) | 지연 |
|---|---|---|---|---|
| 10-24(토) | `0 22 * * 5` | 07:00 | 09:05 | **2시간 5분** |
| 10-26(월) | `0 22 * * 0-4` | 07:00 | 08:46 | **1시간 46분** |

두 번 다 1~2시간이고, 둘 다 **정각(분 0)** 이다. GitHub Actions 의 예약 실행은 정각에 요청이
몰려 큐가 길어진다 — 가장 흔한 완화책이 **정각을 피해 어중간한 분으로 옮기는 것**이다.
워크플로 상태는 둘 다 `active` 이고 비활성화나 cron 문법 문제는 아니다.

### 판단

고장이 아니므로 고칠 것은 없고, **받는 시각을 당기는 조정**만 남았다.
정각을 피해 `53 21 * * 0-4`(= 06:53 KST)로 옮기는 것을 후보로 둔다.
지연이 정각 혼잡 탓이면 07:00 근처에 들어오고, 그래도 밀리면 지금보다 7분 빠를 뿐 손해는 없다.

### 남은 의문 — 예약 실행이 왜 안 떴나

| 가능성 | 판단 |
|---|---|
| GitHub cron 지연 | 가장 유력. 10-24 에 2시간 5분 늦은 전례가 있다 |
| 05:40 까지 파일이 무효였던 영향 | 무효 상태는 05:42 에 풀렸고 예약은 07:00 이라 무관해 보인다 |
| 60일 비활성 비활성화 | 아니다. 커밋이 계속 들어가고 있다 |

내일(10-27) 07:00 에 자동으로 뜨는지가 판정이다. 또 안 뜨면 지연이 아니라 구조 문제다.

## 2026-10-26 (월) — 어제 고치면서 daily.yml 을 깨뜨렸다 (05:40 발견·수정)

어제 10-25 수정분을 푸시한 뒤로 **푸시마다 `daily.yml` 이 0초 만에 실패**하고 있었다.
`push` 트리거가 없는데도 실행이 잡히는 것이 단서였다 — 파일이 무효라 GitHub 이 트리거를
읽지 못해 푸시에 귀속시킨 것이다. 실행 목록에 워크플로 이름 대신 **파일 경로**가 찍혀 있었다.

- **원인**: 5ad4ca9 에서 넣은 주석 한 줄.

  ```
  # 입력값은 ${{ }} 로 스크립트 본문에 박지 않고 env 로 받는다.
  ```

  `run:` 블록은 YAML 주석이 아니라 **문자열**이다. GitHub 은 실행 전에 그 문자열 안의 표현식을
  먼저 해석하므로, **빈 표현식 하나로 워크플로 파일 전체가 무효**가 된다. `#` 은 런타임의
  PowerShell 주석일 뿐 GitHub 파서에는 아무 의미가 없다.
- `weekly.yml` 은 주석에 같은 기호가 없어 멀쩡했다. 10-25 재발송이 성공한 것도 그래서다.
  **한 파일만 깨졌기 때문에 어제는 드러나지 않았다.**
- PyYAML 파싱은 통과한다. YAML 문법 문제가 아니라 GitHub 의 표현식 검증 단계라서,
  **로컬 YAML 검증으로는 못 잡는다.** 푸시 후 startup failure 유무를 보는 것이 유일한 확인이다.
- **고침**: 주석에서 기호를 빼고 말로 풀어 썼다. 푸시 후 startup failure 없음을 확인했고,
  아까 실패했던 run 의 표시 이름도 파일 경로에서 `오늘의 영어 (월~금 07:00 KST)` 로 바뀌었다
  (= GitHub 이 이제 파일을 읽는다).
- 그대로 뒀으면 **오늘 07:00 평일 발송이 통째로 안 떴다.** 발견 시각 05:40, 여유 1시간 20분.

## 2026-10-25 (일) — Actions 이관 뒤 첫 점검: 두 군데가 막혀 있었다

10-24 이관 후 실제로 도는지 확인하러 들어갔다가, **발송이 아직 한 번도 성공하지 못한 것**을 발견했다.
원인이 두 개였고 서로 무관하다.

### 1. 워크플로의 인자 전달 버그 (고침)

10-24 토요일 복습 발송이 12초 만에 실패해 있었다 (run 40043239322).

```
[FAIL] 주간 발송 실패 — Exception calling "ParseExact" with "3" argument(s):
       "String '-Force' was not recognized as a valid DateTime."
```

- **원인**: `$args = @('-Force')` 뒤 `& ./scripts/send-weekly.ps1 @args`.
  PowerShell 의 **배열 스플래팅은 값을 위치 인자로 넘긴다.** 그래서 문자열 `'-Force'` 가
  스위치 이름이 아니라 **첫 위치 인자인 `-Date`** 에 들어갔다. `$args` 가 자동 변수인 것도 겹쳤다.
- 로컬에서 같은 param 블록으로 재현 확인:

  | 방식 | 결과 |
  |---|---|
  | `$args = @('-Force')` → `@args` | `Force=False  Date='-Force'` ← 실패 |
  | `$p = @{ Force = $true }` → `@p` | `Force=True   Date=''` ← 정상 |

- **고침**: 두 워크플로 모두 해시테이블 스플래팅으로 바꿨다.
  더불어 입력값을 `${{ inputs.* }}` 로 스크립트 본문에 박던 것을 **env 경유**로 바꿨다
  (본문 삽입은 입력에 따옴표가 섞이면 그대로 코드가 된다).
- `-DryRun` 으로 세 경우(주간 스케줄 / 주간 날짜지정 / 평일 번호·강제지정) 전부 통과.
- **`weekly.yml` 은 매주 실패하는 상태였다.** 항상 `-Force` 를 붙이기 때문.
  `daily.yml` 은 스케줄 실행 때 `$args` 가 빈 배열이라 이 버그를 피해 갔고, **수동 실행에서만** 터졌다.

### 2. Secret 두 개가 빠져 있다 (사용자 작업 — 아직 안 됨)

```
등록됨 : KAKAO_REST_API_KEY · KAKAO_CLIENT_SECRET · KAKAO_REDIRECT_URI
필요함 : KAKAO_REST_API_KEY · KAKAO_CLIENT_SECRET · KAKAO_REFRESH_TOKEN · GH_PAT
```

- **`KAKAO_REFRESH_TOKEN` 없음** → 러너에 `state/tokens.json` 이 없으니(커밋 제외) 토큰을
  시작할 밑천이 없다. 버그를 고쳐도 **이것 없이는 발송이 안 된다.**
- **`GH_PAT` 없음** → 갱신 토큰 회전분을 Secret 에 다시 못 쓴다. 당장은 안 죽지만 2개월 뒤 조용히 멎는다.
- `KAKAO_REDIRECT_URI` 는 어느 워크플로도 쓰지 않는다. 둬도 해는 없다.
- 로컬 `state/tokens.json` 의 refresh token 은 **2026-12-21 까지 유효**하다 (10-23 발송 때 갱신된 것).

### 3. 알아 둘 것 — Actions 의 cron 은 정시가 아니다

10-24 실행은 예약(UTC 금 22:00 = KST 토 07:00)보다 **2시간 5분 늦은 KST 09:05** 에 떴다.
GitHub 이 부하에 따라 스케줄 실행을 미루거나(드물게) 거르는 것은 문서화된 동작이고, 고칠 방법이 없다.
"07:00 정각"이 필요하면 Actions 는 맞지 않는다. 아침에 받기만 하면 되는 용도라 그대로 둔다.

### 4. 해결 — Actions 첫 발송 성공 (22:55)

  소진하지 않아 10-26 예약분이 밀리지 않는다.


- "갱신 토큰 변화 없음"은 정상이다. 카카오는 만료가 가까울 때만 refresh token 을 새로 준다.
